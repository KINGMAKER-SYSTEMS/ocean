De-flaked two timing-sensitive fixtures without weakening either assertion. Daemon: `room_maintenance::tests::an_unknown_directory_goes_and_a_closed_rooms_directory_stays` was reported as capturing `now` before writing the orphan file, but that `now` only feeds retention; the orphan cutoff is `SystemTime::now()` taken inside `run_sweep_into` after the fixture exists, and a 20,000-iteration probe on this APFS volume never saw a file or directory mtime exceed, or even share a microsecond with, the user-space clock sampled after the write, so the clock cannot produce the failure. The real race is the process-global attachment custody `RwLock` in `room_attachments.rs`: the orphan pass used a hardcoded `try_cleanup_guard()` and silently `continue`d whenever any other fixture in the same test binary held publication (uploads) or cleanup (retention) custody, which reproduces deterministically as `orphan_dirs_removed` left 0 right 1 with `error: None` when a foreign publication guard is live; an instrumented full-suite run showed the only deferral in the wild was the deferral fixture's own, consistent with the rare rate reported. Fix: custody acquisition is now a parameter of `run_sweep_into`/`run_orphan_gc_at` (a `CleanupGuard` alias names it); the daemon passes `try_cleanup_guard` unchanged and still defers a busy publisher, the `#[cfg(test)]` `run_sweep` and every classification fixture pass the awaited `cleanup_guard`, and only the deferral fixture keeps the production acquisition; the eight-parameter seam signature carries a justified `too_many_arguments` allow. A scratch fixture holding publication custody on another thread for 300 ms failed 3/3 before the change and passed 3/3 after it (removed before commit). Tauri: `watch_admission_tests::scoped_native_watch_release_keeps_alias_peer_and_legacy_watch_live` is a test-fixture problem, not a code ordering bug: `admit_watches` and `retire_scoped_paths` are pure map operations, while notify's FSEvents `watch()` returns once the stream is scheduled on its run loop and before fseventsd is delivering for it, so a write landing in that window is never reported and the 10 s `recv_timeout` `.expect` fires (notify's own suite sleeps after `watch()` on macOS for this reason). The unmodified test passed 20/20 solo and 5/5 in-suite on this machine, so the reporter's load-dependent rate was not reproduced locally. Fix in the test: the callback now carries event paths, every stream (old, new, peer, legacy) must report a probe write before the release, survivors are judged by path on a second file `.git/live` (ancestor paths accepted for OS rescans), and any report from the released stream fails the fixture, a stronger assertion than before.
